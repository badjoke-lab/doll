# Portable Memory Is Not AI Continuity: PAM, PLUR, PROJECTMEM, and doll

**Status:** Publication-ready draft; non-normative  
**Date:** 2026-08-12

AI systems are beginning to acquire “memory,” but that word hides several different engineering problems.

One system may define a format for moving remembered facts between assistants. Another may focus on deciding which memories should be recalled. A third may preserve the history of a software project so an agent does not repeat yesterday's failed fix. A fourth may try to preserve an entire user-owned AI working environment across model, provider, runtime, and application changes.

Those systems can look similar from a distance because all of them talk about persistence. They are not solving the same problem.

This article compares four approaches:

- **Portable AI Memory (PAM)** — a general interchange format for AI memory;
- **PLUR** — an adaptive persistent-memory design built around Engrams;
- **PROJECTMEM** — a local-first event-sourced memory and judgment layer for coding agents;
- **doll** — a user-owned personal AI continuity system in active development.

The comparison matters because the wrong abstraction can create a new form of lock-in while trying to solve the old one. If a portable-memory format becomes the only representation of project state, it may be too narrow. If an embedding index becomes authoritative, changing embedding models can damage continuity. If a project event log becomes a permission system, historical observations can acquire authority they were never meant to have.

The useful question is therefore not “Which one has the best memory?”

It is:

> **Which part of continuity is each system responsible for?**

## The short version

The four systems occupy different layers.

| System | Primary problem | Canonical idea | Strongest contribution | What it is not |
| --- | --- | --- | --- | --- |
| PAM | Move memories between systems | Versioned JSON interchange | Portable semantic memory and provenance | An application storage model or runtime protocol |
| PLUR | Make persistent memory improve through use | Engrams plus activation, feedback, episodes, and retrieval | Adaptive recall and consolidation | A complete user AI-environment continuity layer |
| PROJECTMEM | Stop coding agents from forgetting project experience | Append-only project events plus deterministic projections | Failed-attempt memory and pre-action judgment | A general personal memory interchange standard |
| doll | Preserve a user-owned AI working environment across replacement and failure | Versioned authoritative state plus portable/recovery representations | Continuity across memory, project state, authority, models, portability, backup, and recovery | A claim that every subsystem must use one memory format |

This is not a ranking. PAM can be better at interchange while PLUR is better at adaptive recall and PROJECTMEM is better at representing failed attempts. Doll can still need all three ideas while remaining architecturally broader than any one of them.

## 1. PAM: memory as an interchange problem

Portable AI Memory is the cleanest of the four to classify because its specification explicitly defines its scope.

PAM v1.0, published on February 17, 2026, describes itself as an **interchange format** for user memories generated by AI assistants. It explicitly says it is **not a storage format**. Implementations may use SQLite, PostgreSQL, vector databases, graph databases, or other internal representations, while importing and exporting PAM at the boundary.

That distinction is important.

A system does not have to reorganize its entire internal database around PAM in order to support PAM. PAM plays the role that vCard plays for contacts: it defines a portable representation at the edge.

A PAM export has a required `memory-store.json` and may include separate conversation files and embeddings. A memory carries semantic content, temporal metadata, provenance, lifecycle information, optional confidence and access metadata, relations, and an optional embedding reference. The specification also defines integrity behavior, incremental exports, and optional signatures.

For a continuity-oriented system, this is valuable because it creates a plausible common denominator for moving memory without making one provider's export format the de facto standard.

But PAM deliberately leaves several things outside its scope. It is not a complete project-management schema. It is not a capability-permission system. It is not a backup-and-restore architecture. It is not a model-binding record. It is not a runtime protocol.

That is not a weakness. It is what makes PAM usable as an interchange layer.

### What doll should take from PAM

Doll should support PAM through a versioned import/export adapter rather than invent a competing public “Doll Portable Memory Standard.”

The Doll State Package still has a separate purpose. It needs to preserve more than memory: project state, decisions, work items, policies, permissions, provenance, artifacts, model/runtime state, portability reports, migration history, and recovery information.

So the relationship should be:

```text
Doll State
  -> PAM adapter
  -> portable memory subset

Doll State
  -> Doll State Package
  -> broader doll continuity state
```

Those are two different exports for two different jobs.

There is also a subtle implementation lesson. A source format's hash is not automatically a safe internal identity. PAM defines `content_hash` according to its own normalization rules. Doll can calculate and preserve that value for PAM compatibility, but its own canonical identity and conflict logic should remain independent of PAM-specific normalization.

Interchange conformance should not silently redefine internal semantics.

## 2. PLUR: memory as a retrieval and learning problem

PLUR asks a different question:

> Once memory is persistent, how does an agent become better at using it?

Its Engram specification v2.1, dated March 2026, defines persistent memory as individually addressable learned units. An Engram can include a statement, rationale, type, scope, visibility, activation state, usage statistics, feedback signals, associations, temporal information, and episodic metadata.

The reference model separates the durable Engram representation from its search index. The specification describes YAML files as the source of truth and an optional SQLite search index that can be rebuilt. This is a strong continuity property in miniature: losing the index should not mean losing the memory.

PLUR also distinguishes Engrams from episodes. Engrams represent learned knowledge; episodes preserve timestamped event history. Its retrieval model includes lexical and semantic search, activation and decay, feedback, and association-aware ranking.

This is where PLUR is substantially ahead of doll's current implementation.

As of August 12, 2026, doll's accepted local search is deliberately simple: deterministic, read-only Unicode-normalized substring matching over active non-secret local records. It uses no model, no network, and no persistent semantic index. That simplicity was intentional because the continuity and authority boundaries had to be proven first.

PLUR shows what the next layer can look like once those boundaries exist.

### What doll should take from PLUR

Doll should adopt the **separation between canonical memory and rebuildable retrieval machinery**, and it should add a feedback-aware recall layer.

It should not copy activation or decay directly into the lifecycle of authoritative memory.

That distinction matters because “unlikely to be recalled” and “no longer true” are not the same thing.

Suppose a user has a confirmed memory saying:

> Production deployments require manual approval.

If that memory is not used for six months, its retrieval priority may reasonably fall. But the rule does not become false. It should not be archived or deleted because an activation score decayed.

Doll's specification now separates three things:

```text
Authoritative MemoryRecord
        |
        +--> MemoryUsageSignalRecord
        |       recalled / helpful / irrelevant / contradiction surfaced
        |
        +--> derived RecallState
                lexical score
                semantic score
                recency
                usefulness
                ranking
                embedding/index references
```

The MemoryRecord keeps meaning and authority. Usage signals preserve bounded evidence about use. RecallState is rebuildable.

If the embedding model changes, ranking may change. The memory should not.

If the vector index is deleted, search quality may temporarily degrade. The memory should still be inspectable, exportable, restorable, and recoverable.

This is one of the clearest places where a memory-engine concept can improve doll without becoming doll's canonical architecture.

## 3. PROJECTMEM: memory as project experience and judgment

PROJECTMEM is narrower in domain than PAM or doll, but it exposes a problem that general personal-memory systems can easily miss.

Coding agents do not only forget facts. They forget **attempts**.

That is expensive.

An agent can reopen a repository, rediscover the same bug, try the same approach that failed yesterday, and spend another context window proving the same dead end.

PROJECTMEM treats this as a first-class problem. Its paper describes a local-first, event-sourced memory and judgment layer for AI coding agents. Development history is recorded as append-only typed events and projected deterministically into compact summaries. A pre-action gate warns before an agent repeats a known failed approach or edits a fragile file.

The current v0.2.0 repository has evolved beyond the original paper. The repository describes 15 native MCP tools, while the June 2026 paper described 14. The current implementation also separates `plan.md` — mutable intent, what should happen — from the append-only event history — what did happen.

That separation is particularly useful.

Current-state planning and historical experience are different data structures.

### What doll should take from PROJECTMEM

Doll already has more formal current project state than PROJECTMEM needs for its core purpose. It has ProjectRecord, DecisionRecord, WorkItemRecord, ProcedureRecord, ProjectCheckpointRecord, deterministic project status, and Resume Bundles.

But doll has a gap between that current state and its operational audit log.

An audit event can answer:

> Which actor performed which state operation, and did it succeed?

It does not naturally answer:

> What did we try, what happened, and what did we learn?

Those should be separate records.

Doll's specification now defines a future `ProjectExperienceRecord` to fill that gap with semantic event kinds such as:

- observation;
- hypothesis;
- attempt;
- outcome;
- resolution;
- lesson.

A failed attempt can remain part of the project history even after the current WorkItem moves forward. If the historical record later proves wrong, a correcting or superseding event can be appended rather than silently rewriting the old event.

This borrows event-sourcing where event history is useful without converting all Doll State to event sourcing.

That distinction is deliberate. Current permission, policy, project status, model bindings, and work-item state still benefit from explicit revisioned current representations.

### Memory-as-Governance, generalized carefully

PROJECTMEM's most interesting idea is its pre-action gate: memory should not only be available after the agent asks for it; it should be able to warn before a known mistake is repeated.

Doll generalizes that idea in its specification as a deterministic `ContinuityPreflight`.

Before a proposed action, preflight can check:

- applicable policy;
- permissions;
- governing decisions;
- approved procedures;
- current blockers;
- prior failed ProjectExperienceRecords;
- capability and confirmation requirements.

But doll makes one important distinction from a broad “memory as governance” framing:

> **Experience can inform authority without becoming authority.**

A prior failed attempt normally deserves a warning. It does not automatically become a permanent prohibition.

A hard deny should still come from an authoritative PolicyRecord, PermissionRecord, blocker, capability rule, or other explicitly accepted authority source.

An imported event saying “never do this again” is evidence, not a permission rule.

This preserves the value of pre-action memory without creating a second, implicit security system.

## 4. doll: memory as one part of continuity

Doll began from a broader failure scenario.

What happens if the model disappears?

What happens if the provider becomes too expensive, a cloud account is lost, a runtime is abandoned, a preferred UI breaks, a machine dies, or the doll project itself stops being maintained?

If the only durable object is “memory,” the user may still lose the environment that gives that memory operational meaning.

Doll therefore treats the following as continuity state when applicable:

- confirmed memory;
- preferences;
- policies and prohibitions;
- permissions and capability settings;
- projects and decisions;
- work items and blockers;
- procedures and checkpoints;
- conversations and artifacts;
- source, claim, evidence, and provenance records;
- model and runtime manifests;
- explicit model/runtime bindings;
- import mappings and loss reports;
- backup and migration metadata;
- restore and recovery paths.

The key architectural phrase is:

> **Local-complete, cloud-optional.**

Cloud models can improve capability. They cannot own the continuity path.

This makes doll broader than a portable-memory system, but it also means doll should resist the temptation to invent proprietary versions of every adjacent standard.

A continuity layer should be able to use PAM for memory interchange, an MCP interface for agent access, an optional semantic-search engine for recall, and product-specific adapters for PLUR or PROJECTMEM without making any of them the only way to interpret the user's state.

## 5. The most important comparison: what is authoritative?

The architectural differences become clearer when the question changes from “What data is stored?” to “What data is allowed to change the system?”

| Question | PAM | PLUR | PROJECTMEM | doll direction |
| --- | --- | --- | --- | --- |
| Is the format itself canonical application storage? | No; interchange format | Engram YAML is reference source of truth | Append-only project event log is core history | Versioned Doll State is canonical |
| Are embeddings required to preserve memory meaning? | No; optional | Semantic retrieval may use embeddings | No | No; derived and rebuildable |
| Can retrieval strength change semantic truth? | Not its main concern | Activation/decay influences retrieval lifecycle | Not the main model | No; recall and truth are separated |
| Are failed attempts first-class? | Can be represented only as memory content/metadata, not its central abstraction | Episodes/Engrams can capture experience | Yes; central feature | Specified as future ProjectExperienceRecord; not yet implemented |
| Is current project work state first-class? | No | Not the core scope | Issue/plan/project memory focused | Yes; Project/WorkItem/Decision/Procedure/Checkpoint |
| Does imported content automatically gain local authority? | Format defines portable fields, not Doll authority | Implementation-specific | Project memory is used by its own judgment layer | No; imported content remains data until promoted |
| Is there a complete backup/restore continuity contract? | Outside PAM scope | Not the primary specification scope | Local project files/history focus | Yes; explicit package, backup, restore, migration, recovery |
| Is model/runtime replacement part of the state contract? | Provider-neutral interchange helps memory portability | Multi-agent memory reuse is a goal | Agent-independent project memory is a goal | Yes; explicit model/runtime/binding continuity |

This table also shows why simply choosing one project as “the standard” would be the wrong design move.

They have different centers of gravity.

## 6. What doll should borrow — and what it should refuse to copy

The comparison produces a fairly concrete implementation strategy.

### From PAM: borrow the boundary

Use PAM as the first general memory import/export profile.

Do not replace Doll State with PAM. Do not market PAM export as a complete doll backup. Do not copy foreign access metadata into local permissions.

### From PLUR: borrow the retrieval intelligence

Add usage signals, derived recall state, optional local semantic retrieval, ranking, and consolidation review.

Do not let activation or decay silently archive confirmed memories. Do not make embeddings authoritative. Do not require a vector database for local startup or recovery.

### From PROJECTMEM: borrow semantic experience and pre-action checks

Add append-oriented project experience for observations, hypotheses, attempts, outcomes, resolutions, and lessons. Use those records in a deterministic preflight so previous failures can be surfaced before they are repeated.

Do not replace all current state with an event log. Do not let imported events, model-generated plans, or remembered warnings become permission authority by themselves.

### From MCP: borrow interoperability, not persistence

MCP is useful as a tool and agent interface. It should not become the canonical storage format.

A sensible initial doll MCP surface is scoped read-only inspection and proposal creation. Direct permission grants, high-risk confirmation, procedure approval, checkpoint confirmation, secret retrieval, or WorkItem completion should remain outside protocol content authority.

## 7. The roadmap consequence

This comparison does change doll's roadmap, but not its foundation.

The previous sequence — continuity first, safety before model authority, canonical portability before provider-specific integration, local before cloud — still holds.

The new work is inserted after the existing IMP-083 frontier in dependency order:

1. keep the current explicit context-selection path;
2. separate memory-use signals and derived RecallState from authoritative MemoryRecord;
3. improve local retrieval from lexical scoring toward optional local semantic search;
4. add review-controlled consolidation;
5. implement PAM v1.x import/export through the existing portability boundary;
6. add ProjectExperienceRecord with State Package, backup, restore, and fresh-process coverage;
7. add deterministic ContinuityPreflight;
8. treat PLUR, PROJECTMEM, and MCP as later interoperability adapters/interfaces unless a concrete need moves a bounded slice earlier;
9. keep complete Doll State Package signing in the long-term-operation phase.

IMP-083 itself is a bounded local resource-measurement and evidence step. It does not implement the memory-interoperability, adaptive-recall, or project-experience work described above.

The sequencing is important.

Semantic retrieval should not arrive before the system knows how to lose and rebuild an index safely. A pre-action warning system should not arrive before project experience has a trustworthy representation. An external adapter should not define canonical state accidentally.

## 8. A more useful definition of “AI continuity”

The comparison suggests a definition that is more precise than “persistent memory.”

### Memory portability

Memory portability is the ability to move remembered semantic information between systems while preserving enough identity, provenance, temporal meaning, and relationships to remain useful.

PAM is explicitly aimed at this problem.

### Memory continuity

Memory continuity adds the requirement that remembered information remains interpretable when a model, runtime, retrieval index, or application changes.

PLUR's rebuildable index direction and doll's model-independent state both touch this layer.

### Project continuity

Project continuity preserves not only remembered context, but the current state and history of work: objectives, decisions, blockers, procedures, attempts, evidence, and resumption state.

PROJECTMEM is especially strong on experiential history; doll's current model is stronger on explicit current project state.

### AI-environment continuity

AI-environment continuity is broader again.

It asks whether a user can replace or lose the model, provider, runtime, UI, machine, or upstream project and still recover the user-owned state required to inspect, resume, migrate, and safely operate the environment.

That includes memory, but memory alone is not enough.

A useful shorthand is:

> **Memory asks what the next model should remember. Continuity asks what must survive when the model itself is gone.**

## 9. Why open standards still matter to a broader continuity system

Calling doll a continuity layer should not become an excuse for a larger proprietary format.

The opposite should happen.

The broader the internal state becomes, the more important it is to use narrow standards at the boundaries where they fit.

- Memory interchange: PAM where compatible.
- Agent/tool access: MCP where compatible.
- JSON canonicalization for cryptographic meaning: an established standard such as RFC 8785 when needed.
- Package signatures: reviewed cryptographic primitives and libraries, not custom crypto.
- Product-specific migration: versioned adapters with explicit loss reports.

Doll's own State Package remains justified only for the information that cannot be faithfully reduced to those narrower standards without losing continuity semantics.

The goal is not to make every tool speak Doll State.

The goal is to make Doll State escapable, inspectable, and interoperable enough that doll itself does not become the final lock-in point.

## Conclusion

PAM, PLUR, PROJECTMEM, and doll overlap, but the overlap is more useful as a map than as a competition.

PAM provides a promising interchange boundary for portable memory.

PLUR demonstrates how persistent memory can become adaptive through retrieval, feedback, and consolidation while keeping its primary representation separate from a rebuildable index.

PROJECTMEM demonstrates the value of append-only project experience and of surfacing previous failures before an agent repeats them.

Doll's role is different: preserve the user-owned continuity that gives those memories and experiences meaning when the model, provider, runtime, interface, machine, or application changes.

That leads to a design principle that is likely to matter beyond doll:

> **Do not ask one memory system to become the entire continuity system. Define the boundaries, keep authority explicit, and make each replaceable layer portable at the level where it actually belongs.**
