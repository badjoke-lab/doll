# IMP-097 — Lite client performance evidence interpretation

Status: implemented for Issue #309.

## Purpose

IMP-097 interprets the accepted IMP-096 primary Intel Mac real-machine measurement without converting one bounded `doll-lite-client-only` observation into unsupported full Lite hardware requirements.

Source evidence:

`docs/testing/results/IMP-096-primary-intel-mac-lite-client-resource-measurement.json`

Measured commit:

`b57ebe6fb4a7620901b95b49f6743b71ae1026f7`

The interpretation is generated by:

`scripts/interpret_imp_097_lite_client_performance.py`

and recorded at:

`docs/testing/results/IMP-097-lite-client-performance-interpretation.json`

## Accepted observation

The source evidence first passes the existing IMP-096 deterministic validator and exact measured-commit binding. The accepted bounded observation remains:

- Darwin `x86_64`;
- CPython `3.14.6`;
- `doll-lite-client-only` measurement scope;
- total bounded workload duration `256372493 ns`;
- process peak RSS `41291776 bytes`;
- measured synthetic workspace `86369 bytes` across 2 files and 7 directories;
- zero measured-workload network attempts;
- zero measured-workload process-launch attempts;
- no model execution;
- no external runtime, model, or GPU memory measurement.

These are observations from the accepted primary Intel Mac run. They are not release requirements.

## Deterministic interpretation

The version-1 interpretation records two positive claims only:

1. the bounded client workload was observed successfully on the primary Intel Mac under the measured conditions;
2. the client-only evidence has been interpreted against the accepted release boundary.

It explicitly keeps the following false:

- minimum RAM requirement defined;
- full-install disk requirement defined;
- user-visible latency requirement defined;
- external runtime memory requirement defined;
- model memory requirement defined;
- GPU memory requirement defined;
- total-system resource requirement defined;
- cross-machine generalization supported;
- full Lite performance thresholds defined;
- Lite performance gate complete;
- Phase 6 complete;
- Lite v1.0 complete;
- accessibility gate complete;
- release-candidate soak complete.

This avoids treating process RSS as installed-system RAM, synthetic workspace bytes as full installation/model storage, or harness duration as a user-visible latency target.

## Required future evidence

Before full Lite performance requirements can be declared, the interpretation keeps these evidence classes visible:

- representative local runtime and model resource measurement;
- repeatability and variance evidence;
- full installation and model storage measurement;
- user-visible latency workload measurement;
- release-candidate soak disk-growth evidence.

Additional cross-machine evidence is required before broadening any performance claim beyond the primary machine.

## Failure boundary

IMP-097 does not reinterpret malformed or weakened evidence. The existing IMP-096 validator runs first, so a wrong commit, non-real-machine evidence, changed measurement scope, privacy failure, invented source thresholds, model/runtime inclusion, measured network/process activity, or release overclaim fails before interpretation.

## Non-claims

IMP-097 does not establish minimum RAM, required free disk, supported model size, response-time budgets, Ollama/model/GPU memory requirements, total-system performance, accessibility acceptance, the seven-day soak, complete Phase 6, Lite v1.0, or stable general anti-lock-in.
